# 训练反馈

## 何时使用

当用户记录一次训练，或描述训练感受、配速/均速/功率、心率、疲劳、疼痛时使用。用户发送训练截图、手表截图、码表截图时，也应在图片识别完成后使用。

注意：`workout-feedback` 不是孤立评价单次训练。它必须结合用户最近的身体状态、疼痛、睡眠、疲劳、恢复趋势，以及系统生成的 active 训练计划；数据持久化由 `training-memory` 负责，两者可同时调用。

所有项目先参考 `../../docs/endurance-training-methodology.md` 的统一反馈闭环：同时解释外部输出、内部成本、机械/技术负荷和非训练压力，不用单一设备分数裁决。

跑步训练反馈应参考 `../../docs/running-coach-principles.md`。这些原则只作为教练判断层，不替代用户自己的近期数据和安全规则；重点关注跑步经济性、配速纪律、恢复窗口和长距离补给。

## 需要收集的输入

必须尽量识别：

- 日期（缺省默认今天）。
- 运动项目（跑步/骑行/游泳/铁三赛段）。
- 距离或时长。
- 配速（跑步）/ 均速或功率（骑行）/ 每 100 米配速（游泳）。
- 主观感受。
- 疲劳程度（文字或 1-10）。
- 是否疼痛。
- 是否按计划完成（如有计划）。

如果输入来自图片识别结果，优先使用识别出的字段；识别不确定的字段不要强行补全。

可选识别（有则参考，无则跳过，不追问）：

- 平均心率、最高心率。
- 天气、路线海拔/爬升。
- 睡眠和压力。
- 鞋子、车、泳池/公开水域等装备或环境变化。

## 反馈前的必要上下文

给单次训练反馈前，必须尽量读取或参考当前用户自己的近期状态：

- 最近 7 天训练记录：训练次数、总量、最长训练、强度分布。
- 最近 7 天身体状态：疲劳、睡眠、压力、恢复。
- 最近 14 天疼痛记录：部位、程度、是否重复出现、是否加重。
- 最新有效系统计划：读取 `training_plans.status = active` 的计划，并按同日同项目从 `planned_workouts` 查找计划训练。
- 匹配训练的 `planned_workout_steps`，以及 Garmin 原始活动详情中的 `splits.lapDTOs`；标准圈段缺失时才查看 `typed_splits.splits`。
- 当前项目有效的 `training_zone_sets`；结构化反馈保留 `zone_set_id`，用于追溯能力锚点和算法版本。
- 最近一次用户明确说的目标或当前阶段：恢复期、打基础、备赛、比赛后恢复等。

如果系统暂时无法读取历史，也要在回复里说明“先按你这次提供的信息判断”，不要假装已经结合历史。

## 行为规则

- 优先快速识别并给反馈，不要先要求用户补全所有字段。
- 图片消息必须先识别图片内容；识别失败时只请用户补一句关键字段，不做假分析。
- 缺少日期时默认今天；缺少训练类型时按用户语义推断（轻松跑/长距离/骑行/游泳等）。
- 先把本次训练写入训练记录；如果消息里包含疲劳、睡眠、压力、疼痛、恢复，也同步写入身体状态记录。
- 如果存在 active 系统计划，默认按训练日期、sport_type 和 discipline 匹配同日同项目的 `planned_workouts`；唯一匹配时写入 `workout_logs.planned_workout_id`，多个候选时不自动关联。
- 再结合计划训练和近期身体状态判断计划完成情况：按计划完成 / 部分完成 / 超量完成 / 偏离计划 / 无计划可比对。
- “完成度”描述本次训练本身是否完成；“计划完成情况”只描述与系统训练计划的关系。
- 风险等级必须同时考虑本次训练和近期身体状态，不能只看本次配速或距离。
- 有有效区间时，用本次可比的功率、心率或配速判断大致落区，并在反馈中保留 `zone_set_id`。整段平均功率、心率或配速只能估计总体强度，不能冒充逐段时间分布。
- 计划含结构化步骤、Garmin 又有圈段时，先展开重复组，再比较圈段数量。只有计划展开后的步骤数与 Garmin 圈段数量完全一致，才按顺序计算逐段完成度；数量不一致时必须说明原因，不强行匹配。
- 逐段时长或距离允许约 ±10% 的执行波动；逐段强度只使用同一圈段的平均功率、平均心率或由距离和时长推算的配速，并与该步骤保存的版本化区间比较。缺少圈段指标时写“仅确认时长”，不从全程均值倒推出每一段。
- 完成逐段分析后，把评估头写入 `workout_step_assessments`，把每一步的时长、强度和总体结果写入 `workout_step_results`；同一训练重复分析时幂等替换，不累积重复快照。
- 即使圈段数量一致，自动圈也可能与训练步骤恰好同数，因此逐段顺序匹配最高只写“置信度为中”，并提醒结合设备训练设置和主观感受复核。心率间歇还要考虑滞后，不能单独裁决短段质量。
- 没有可用且未过期的专项能力锚点、区间已过期，或本次缺少可比指标时，明确退回 RPE 与谈话测试，不虚构精确区间。
- 然后给出下一次训练建议。
- 用户超量完成时，不要盲目表扬，应提醒恢复。
- 用户少练时，判断原因（疲劳/时间/疼痛），而不是直接批评。
- 出现疼痛时，优先建议降负荷，必要时调用 `injury-risk`。
- 分析结束后，更新用户身体状态：疲劳、疼痛、恢复建议和下一次观察点。
- 如果本次训练反馈改变了对用户状态的判断，例如“恢复不足”“疼痛风险升高”“疲劳较高”，必须把这个判断沉淀到身体状态或 AI 反馈里，供下次建议使用。
- 如果匹配到计划训练，把计划完成情况和复盘建议写入 `ai_feedback`，并同步更新 `planned_workouts.status`。

## 中长跑反馈规则

- 跑步训练不只看配速，还要看心率、体感、后半程是否掉速、是否出现步频/步幅或动作异常。
- 评价跑姿时聚焦“是否省力”：放松、协调、减少制动和无谓动作，不把前掌或后跟着地当作唯一标准。
- 不用 180 步/分钟作为统一目标。步频和步幅只与用户自己的相近配速、坡度和疲劳条件比较；需要调整时只给小幅、短段尝试。
- 用户刚换鞋、改着地方式、明显缩短/拉长步幅时，把小腿、跟腱、足底和膝部列为负荷转移观察点，不承诺某种技术一定防伤。
- 长跑、半马、全马专项、铁三跑步段和超过 60 分钟的耐力训练，如果前快后慢、心率漂移明显或后半程体感崩，优先提醒配速纪律。
- 用户超量完成、完成长距离、下坡多、比赛或连续关键课后，不盲目表扬；先判断恢复窗口是否足够。
- 超过约 60 分钟的训练、热天训练或长距离专项课，简短提醒补水补碳是否已经在训练中演练。
- 高温高湿下同配速心率或 RPE 升高时，先按环境修正评价，建议按体感/谈话测试降速并补水，不直接判断能力退步。
- 寒冷天气或强度课前提醒渐进式动态热身；训练中断、疾病或伤病后复跑，先恢复轻松有氧和规律，再恢复总量与强度。
- 只有用户提到跑姿、步频、步幅、疼痛、视频或截图时，才展开技术动作分析；普通反馈只给一条最关键动作提示。

## 输出格式

```text
训练反馈：
- 项目：
- 完成度：
- 计划完成情况：
- 逐段完成度：匹配段数 + 时长/强度结论；或圈段数量不一致、未强行匹配
- 结合身体状态：
- 训练质量：
- 强度区间：区间结论 + zone_set_id（有有效版本时）/ RPE 与谈话测试（回退时）
- 疲劳/风险：低 / 中 / 高
- 需要注意：
- 下一次训练建议：
- 已更新身体状态：
```

## 风险信号

出现以下情况时提高风险等级：

- 局部疼痛（任何运动项目）。
- 疼痛随训练加重。
- 连续多天疲劳。
- 同类型训练配速/均速明显下降但主观强度升高。
- 心率异常升高（与平时同强度训练相比）。
- 睡眠差且仍安排强度训练。
- 周训练量、关键课密度或跑步冲击相对个人近 3–4 周基线突然增加；百分比只作观察信号，不作统一安全线。

## 身体状态更新规则

分析后需要更新或补充身体状态：

- 用户提到“累、腿沉、状态差、恢复不好” → 记录疲劳/恢复状态。
- 用户提到睡眠、压力、食欲、精神状态 → 记录到身体状态。
- 用户提到疼痛、紧、酸、麻、胀 → 记录疼痛或不适部位；如果没有部位，只问 1 个问题。
- 用户明确说“没疼、无痛、没有不适” → 记录为无疼痛。
- 如果训练表现明显异常，例如同等强度心率更高、配速下降但体感更累 → 记录为恢复观察点。

不要只在回复里说“注意恢复”，还要让这个状态进入后续上下文。
