# 训练计划制定能力：方法论草案（待用户讨论）

## 2026-10-28 实现进展与对话来源

已核对用户此前提供的豆包训练计划讨论。用户最后确认的排课偏好是：专项关键课可以按项目板块聚焦，低强度有氧可在跑、骑、游之间穿插；两个关键课窗口、关键课后缓冲、较轻的一周以及双练都应作为可选择的上下文，而非所有人的固定模板。豆包文本中的具体跑量、骑跑转换距离、功率/TSS 推算和成绩保证不作为产品规则。

当前已实现：目标新增、替换、删除均经草案与确认；替换和删除保留旧记录历史，并使关联计划显示需要复核。七天预览可接收专项重点、关键课偏好日和有氧穿插偏好；训练量预算读取最近四个连续七天窗口的有效活动，连续训练且当天低风险时可小幅推进，或从一次较轻周向既有稳定量回归；近期突增、中断和状态未知时不据此加量。七天无活动时，自动生成的草案只给至多两节短时轻松课，三项目请求可至多三节，每节不超过 30 分钟。这些预算与起步限制都是待复核的产品启发式，不是个体安全阈值。`preview_plan_blocks` 支持 2–12 周重点项目轮换，只为首周生成逐日草案，未来周显示条件性周量上限预测。`review_plan` 检查目标及训练数据变化，`preview_plan_update` 为下一周重新读取证据并生成差异草案，确认后才保存新版。用户指定完整七天课程时，可逐课保存一天两练、骑跑转换的骑后跑顺序及各项目距离；距离只来自明确输入，不由时长推测。尚未实现自动确认的多周训练量渐进、自动生成双练、个体化赛事减量和基于测试的精确项目处方。

用户自行调整训练时，`review_plan` 会从新活动中提取同日的可能偏差；多条活动、不同来源或缺少数据时不自动认定某节课已完成或跳过。`preview_plan_adjustment` 只改本周尚未发生的一节课，支持跳过、缩短、以低强度换成计划内其他项目或移到可用日；不增加总量、不自动补关键课，当前安全状态变化或来源数据变化会阻止旧草案确认。对多节课或整周结构变化，应重新预览计划，而不是叠加多个未确认的局部修改。

逐课目标可以只指定距离、只指定时间或两者都指定。距离单独输入时，计划时长与分钟数代理负荷保持未知；时间单独输入时，距离保持未指定。若有课程缺少时长，总时长不输出一个误导性的完整数字，而是显示未知及已知分钟数。每日和每周可用时间也可不提供，但产品会标出无法完成的容量核验；已提供的时间限制仍对已知分钟数生效。没有完整首周时间信息或周时间上限时，多周预测不展示数值周量上限。

自动同步发现已批准计划周内的新活动时，现有通知 Inbox 会给出计划复核提醒；这是一条待核对的行动提示，不代表完成率或训练效果。用户确认真实执行与接下来的可用时间后，再预览相应调整。

当前 `expected_load` 字段只保存计划分钟数的占位代理，不能解释为设备训练负荷、TSS 或跨项目可比较的生理压力。没有最近七天训练记录时，单次预览采用 30 分钟的保守产品上限并限制课次数；这是待验证的起步假设，输出应披露，不能声称为个体安全阈值。

用户已确认的训练喜好单独保存在私有 `training-preference` 版本中，成长画像展示当前版本。新计划优先采用本次明确参数，其次读取已确认档案偏好，最后使用默认值；预览附带偏好记录 ID、实际采用的约束和假设。偏好变化会触发旧计划复核提示，不会静默修改已确认计划。自由文本偏好记忆与此前对话不会自动转换为结构化偏好；用户需看过草案并明确确认。专项板块轮换现可生成多周方向，但每周具体排课必须重新预览和确认。

> 2026-10-27，讨论稿，不是已经上线的计划处方，也不替代医疗或专业教练评估。这里先定义产品应如何决策，再决定算法和交互。不要把个人数据、Garmin 凭据或真实计划写入产品仓库。

## 1. 能力定义

从用户自己的想法出发，共创并确认目标；再结合现实时间约束、既往运动暴露和当前身体状态，生成**可执行、可解释、可修改**的训练计划；训练发生后，用实际完成情况和主观反馈滚动调整。目标不是一次生成一张“完美课表”，而是持续做出有依据的下一步安排。系统负责澄清、评估和提供选项，不替用户决定目标。

这是用户可直接使用的独立产品能力。Trimate Agent 和目标计划 Skill 是产品自有的方法与交互资产；目标共创、计划生成、确认和持久化由宿主无关的应用用例承担，MCP/HTTP 是工具传输层。宿主原生 Skill 安装形式可以不同，未来 Web/App 也应调用同一用例。

第一版建议以**健康成人的耐力运动及配套力量训练**为范围，跑步、骑行、游泳采用同一流程但不同项目规则。青少年、孕产期、重大疾病、术后和损伤康复不套用通用自动计划；相关情境需要专门规则和专业人员参与。

## 2. 证据原则

| 原则 | 依据与产品解释 |
|---|---|
| 先保证可持续，再优化训练量 | [WHO 身体活动指南](https://www.who.int/publications/i/item/9789240015128/)给出人群健康活动基线；[ACSM 2026 力量训练立场文件摘要](https://www.acsm.org/wp-content/uploads/2026/03/Resistance-Training-Position-Stand-infographic.pdf)强调一致性、与目标匹配及循序渐进。人群建议不是每位运动员的比赛处方。 |
| 结合内外负荷与主观感受 | [IOC 运动负荷与损伤共识](https://bjsm.bmj.com/content/50/17/1030.long)建议个体化、反复监测外部负荷、内部反应和主观状态；任何单个指标都不足以识别适应不良。 |
| 滚动个体化，但不承诺特定收益 | 一项 [30 人休闲跑者研究](https://pubmed.ncbi.nlm.nih.gov/35975912/)中，基于 HRV、主观恢复和跑速-心率指标调整训练的组获得更大 10 km 改善。这支持“测试个体化调整”，不构成产品效果保证，也不说明 HRV 可单独决定训练。 |
| 不把某个比例当伤病预测器 | 早期 IOC 共识提出监测快速负荷变化，但后续[方法学批评](https://pubmed.ncbi.nlm.nih.gov/32502973/)指出急慢性负荷比（ACWR）的因果和统计问题。产品可展示变化趋势，不能仅凭 ACWR 阈值宣称或自动判定损伤风险。 |
| 强度分配是选项，不是通用公式 | 不同耐力强度分配在[休闲跑者随机试验 A](https://pubmed.ncbi.nlm.nih.gov/23752040/)和[随机试验 B](https://pubmed.ncbi.nlm.nih.gov/33344993/)中均可能改善表现，比较结果受人群、训练量和方案影响。第一版不硬编码“80/20 必然最佳”。 |
| 身体目标不能压倒健康边界 | [IOC REDs 共识](https://bjsm.bmj.com/content/57/17/1073)提醒持续能量不足可损害健康与表现；产品只识别需要进一步评估的线索，不自行诊断或给出极端能量限制。 |

## 3. 决策流程

### A. 从想法共创并确认目标

用户可以输入朴素意图，例如“想完成半马”“希望体重下降但不影响训练”或“想运动却不知道定什么目标”。目标共创用例先保留原话，区分用户明确表达的内容与系统推断；只追问当前制定目标所必需的信息，例如希望改变什么、何时、可投入多少时间、项目偏好和不可接受的代价。

系统生成一个或多个**目标草案**，列出目标类型、可衡量的进展指标（允许暂缺）、期限、优先级、假设、数据缺口、目标间冲突和可能需要调整的地方。可行性评估应使用当前基线和时间约束，但不把粗略估计包装成保证。用户可修改、拒绝或确认草案；未确认前不保存为生效目标，也不自动开出正式训练计划。AI 可辅助理解语言与解释选项，确定性规则负责字段、冲突和安全边界；没有可用 AI 时保留结构化问答路径。

### B. 建立计划上下文

必须由用户确认：首要目标和优先级、项目、赛事日期（若有）、每周可用日与时间、不可训练日、计划周期、现有伤痛/疾病与禁忌、器材及场地。可选：年龄段、经验水平、既往伤病、偏好和不愿做的训练。此前确认的目标草案应作为计划输入，不重新猜测用户意图。

从本地库读取：最近训练频率、时长、项目分布、关键课与长课、强度/功率/配速（仅在数据可信时）、最近中断、主观 Check-in、睡眠等恢复线索、数据新鲜度和缺口。用户提供的信息与设备观测分开记录，不能把设备估计值伪装成用户确认事实。

### C. 安全和数据门槛

1. 出现胸痛、晕厥、异常呼吸困难等警讯时，停止自动开具训练课，提示寻求及时医疗评估；普通疼痛、疾病或功能受限时，不安排高强度并提示必要的专业评估。[美国心脏协会运动安全提示](https://www.heart.org/en/health-topics/cardiac-rehab/getting-physically-active/develop-a-physical-activity-plan-for-you)提供警讯依据。
2. 没有当天主观状态，不把用户判为“已恢复”；可以生成**保守草案**，但高强度课应等待确认。
3. 训练史不足、设备缺失或同步过期时，降级为保守起步方案，标明假设和低置信度；不填造 HR 区间、乳酸阈值、功率或目标配速。
4. 上述门槛属于产品安全策略，需要与合格专业人员评审，不能用现有 ACWR 数值阈值直接代替医学判断。

### D. 构建基线与目标路径

- 基线分别统计各项目近期训练暴露与变化；游泳、骑行、跑步的分钟数和设备“训练负荷”不能未经校准直接相加比较。
- 区分健康维持、能力提升、赛事表现和复训/恢复等目标；多目标冲突时先让用户排序。
- 对赛事目标，建立“当前水平 → 赛事需求”的阶段路径；对非赛事目标，以可持续习惯和阶段性能力指标为主。
- 初版计划可先覆盖未来数周的方向，但只把未来 7 天作为可确认执行的细节；长周期视图是可修订的预测，不是固定承诺。具体周期长度和项目规则需后续验证。

### E. 排课与渐进

先满足硬约束：可用时间、不可训练日、赛事日、疼痛/疾病限制、每周时长上限、必要恢复间隔；无解时报告冲突，不强行生成。

再优化软目标：项目专项性、连续性、关键训练课分布、容易执行的偏好、适当力量训练。训练类型、频率和强度以既往暴露与目标决定；不把“每周必增 10%”“必做 80/20”“每周必有间歇”写成通用硬规则。跑步/骑行/游泳需各自的课表库与进阶约束。

### F. 每日决策与每周复盘

- 每日根据新数据与简短 Check-in 给出“照常 / 降低 / 替代 / 暂停并评估”的建议；不因单次 HRV、Body Battery 或 ACWR 波动自动提高负荷。
- 每次训练后收集实际完成、RPE、症状和原因；比较**计划与实际**，而不只比较设备记录。
- 每周复盘目标进度、执行率、身体反应和数据缺口，提出新版计划。系统不得静默改写已确认计划；变更需展示差异和原因并由用户确认。

## 4. 产品交互与输出契约

对话流程：`表达想法 → 澄清并预览目标草案 → 用户确认目标 → 补计划所需信息 → 检查安全与数据 → 预览计划草案 → 解释取舍 → 用户修改/确认 → 保存计划版本 → 训练后反馈 → 下一版`。

每份草案至少包含：目标及日期、计划覆盖期、前提假设、各周/各项目总量、逐课日期/项目/类型/时长/强度表达、安排原因、替代课、暂停条件、数据缺口、置信度、证据 ID、与上一版差异。优先使用可理解的 RPE/谈话测试描述；只有个人阈值可靠时才给心率、配速或功率区间。模型负责对话解释和提问，确定性引擎负责约束、安全门槛、版本和保存。

## 5. 与现有实现的差距

当前 `TrainingPlanner.generate` 已用近期已记录的项目时长约束七天预览，保留用户指定的专项重点和关键课窗口；旧 CLI `plan-create` 仍会直接保存，属于已知兼容路径。产品工作流已支持目标草案的新增、替换、删除、确认，计划预览、确认、变化复核与新版草案，以及多周重点轮换预测；确认前检查草案版本、来源数据变化和当天安全状态。尚未建立多周训练量渐进路径、项目专项课库、执行率驱动的自动滚动调整，也不能独立证明真人确认。现有安全规则的 ACWR 固定风险边界不应单独升级为自动排课判据。

建议能力拆分为：`GoalIdeaIntake`（保留用户原意）→ `GoalDraft`（澄清、选项与可行性提示）→ `GoalConfirmation` → `PlanContextBuilder`（带来源与新鲜度）→ `SafetyGate` → `SportStrategy` → `ConstraintSolver` → `PlanDraft`（只读预览）→ `PlanApproval`（确认后保存版本）→ `PlanReview`（实际完成与调整建议）。这复用现有本地数据、报告、计划版本和宿主适配，不在 Prompt 里复制核心规则。目标与计划的草案/确认状态须保存在产品侧，不能依赖某段对话继续存在。

对外工具按目标草案与确认、目标变化预览与确认、单周/多周重点预览与确认、计划复核与新版预览等少量用例设计；Agent 负责对话，工具负责调用，产品服务负责校验和状态变更。本地 MCP 已提供这些基础用例和未完成草案查询；更完整的可行性评估和自动渐进的多周专项处方仍未交付。旧 CLI 的 `plan-create` 当前仍会直接保存，应迁移到同一预览/确认用例或明确保留为高级直接命令。

## 6. 验证标准

- 单元/性质测试：硬约束绝不违反；缺数据不伪造强度；风险门槛始终覆盖优化目标；相同输入和规则版本产生可复现草案。
- 历史回放：只使用当时已知的数据生成计划，防止未来信息泄漏；检查可执行性、计划与实际偏差和异常提示。
- 小规模真实试用：记录接受/修改/完成率、主观负担、告警误报漏报、用户理解度；不以短期体重或“避免伤病”作为未经验证的成功宣称。
- 专业评审：运动训练和运动医学/营养相关人士分别审查项目课库、安全门槛及高风险转介话术。

## 7. 需要与用户确定的产品决策

1. 第一优先场景：跑步赛事、铁三/多项目、一般体能与健康、体重/体成分，哪个先做深？
2. 计划跨度：先做滚动 7 天，还是同时给 8–16 周赛事路径？长周期方案应允许每周修订。
3. 自动化边界：新数据到来后只**提出调整建议**，还是可自动修改未开始的课？本草案建议先采用“建议＋用户确认”。
4. 用户愿意每周/每日补充多少主观信息？它直接影响安全判断和计划个体化程度。

以上数字（如历史观察周数、计划周期）都是待验证的产品假设；除明确引用的人群指南外，不应当成适用于所有人的训练处方。
